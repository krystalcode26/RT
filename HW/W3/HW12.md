### What Spring Boot version have you used?

Generally, people use Spring Boot 2.x or 3.x cause after Spring Boot 2.3, we don’t need to explicitly use @Autowired for constructor injection.
For me, I use Spring Boot 3 with Java 17 which is the minimum Java version and also used with Maven, REST APIs, JPA, Redis components. Another major change is the migration from javax.* packages to jakarta.* packages.

### What annotations have you used in Spring?

I've worked with Spring annotations across IoC, dependency injection, AOP, REST, and validation.

@SpringBootApplication as the entry point, it includes @EnableAutoConfiguration, @Configuration, and @ComponentScan.
It uses @RestController, @Controller for controller layer, @Service for service layer, and @Repository for DAO layer.
If a class does not clearly belong to controller, service, or repository, I can use @Component.

After find classes annotation, it register them as beans across layers 
and handling third-party objects through @Configuration and @Bean. 

For dependency injection, I prefer constructor injection over setter or field injection since it makes dependencies explicit 
and avoid null pointer exceptions, and I use @Autowired to wire them, with @Qualifier and @Primary to resolve conflicts when multiple candidates exist. 

On the AOP and exception handling side, I use @Aspect with @Pointcut and advice annotations like @Before, @After, @AfterReturning, @AfterThrowing, and @Around
to intercept execution at different points and @RestControllerAdvice with @ExceptionHandler for centralized error handling.
 
For REST API design, I use @RequestMapping at the class level and @GetMapping, @PostMapping, @PutMapping, @DeleteMapping at the method level, 
pulling request data with @RequestParam, @PathVariable, @RequestHeader,and @RequestBody.

Finally, for validation I trigger it with @Valid on request bodies and define constraints directly on fields using @NotNull, @NotBlank, and @Size.

### What is @EnableAutoConfiguration?

@EnableAutoConfiguration is a Spring Boot annotation that automatically configures beans based on the dependencies we add to the project. 
It is included inside @SpringBootApplication and can be customized or disabled when needed.

It reduces boilerplate configuration by creating common beans such as DataSource, DispatcherServlet, and JPA components automatically. 
Also, Spring Boot can configure the embedded server Tomcat without extra server installation.

### What are the advantages of Spring Boot Framework?

Spring Boot simplifies application development by providing auto-configuration, starter dependencies, and embedded web servers. 
It reduces boilerplate configuration, speeds up development, and has production-ready features.
It is widely used for building REST APIs and microservices.

Auto configuration - automatically set up common components such as DataSource, JPA, and Spring MVC.

Starter packages like spring-boot-starter-web, jpa, security eliminates dependency version management issues.

Embedded servers like Tomcat, so no need to deploy WAR files to an external server.

### How do you define profile?

A profile in Spring Boot is a way to separate configuration for different environments such as dev, testing, QA, and production. 

By setting the active profile, Spring Boot loads the corresponding configuration files (such as application-dev.yml, application-qa.yml... )and beans. 

we can use the @Profile annotation on a @Configuration class or @Bean method to register beans only when a specific profile is active. 

This keeps environment-specific configuration cleanly separated and making the application easier to manage across different deployment environments.

### Why AOP?

AOP separates cross-cutting concerns from business logic. 
It is used to enhance functionality by breaking the original serial execution flow.
With AOP, Spring can insert extra logic without duplicate code and use when an exception is thrown from a target method.

We define where to apply the logic by using @Aspect and @Pointcut with advice such as before, after, after returning, after throwing, and around.
Ex: logging, login check, security, transaction, exception.

### What are the dependency injection types?

Dependency injection has three types: constructor injection, setter injection, and field injection.

Constructor injection is the recommended way. It makes required dependencies explicit when the bean is created and also helps prevent null pointer exceptions 
because Spring has to provide all required dependencies during application startup.
It is loose coupling and easier to test because we can add mock objects directly.

Setter injection is useful for optional dependencies.

Field injection is simple, but it is not recommend because it hides dependencies and makes testing harder.

This also related to circular dependency, which means bean A depends on bean B, and bean B depends on bean A makes it circular. 
Solution: refactor the design. If we really need to break the initialization cycle, we can use @Lazy.

### How do you implement exception handling in Spring Boot?

I would answer this from two layers: exception definition and exception handling.

For exception definition, it includes checked exceptions and unchecked exceptions in Java. 
In Spring Boot, we define custom runtime exceptions for business errors, such as ResourceNotFoundException, 
DuplicateResourceException, invalid request.

Instead of handle exception in every controller method individually, I use @RestControllerAdvice(@ControllerAdvice + @ResponseBody) with @ExceptionHandler to catch exceptions globally
and return a consistent response body and HTTP status code 404 for not found or 409 for conflicts.

Another way is AOP to handle cross-cutting logic. We use @Aspect, @Pointcut, and advice such as @Before, @After, @AfterReturning, @AfterThrowing, and @Around
to handle exception like logging or monitoring which keeps that logic separate from the core exception handling. 

overall structure: define custom exceptions, handle them centrally with @RestControllerAdvice, and use AOP for observability — which keeps the codebase clean and returns a consistent response structure across API.

### CompletableFuture / multithreading in Spring Framework

CompletableFuture is a Java 8 feature that runs tasks asynchronously without blocking the main thread.
It supports chaining, callbacks, and combining multiple results, which makes it much more practical for real-world use. 
Future can't chain operations or callbacks, and have to call .get() which blocks the thread until the result is ready.

In Spring Boot, I use it together with @Async by enabling async support with @EnableAsync, annotating the method with @Async, 
and returning a CompletableFuture so the caller doesn't have to wait — this is useful for things like sending emails, 
calling external APIs, or processing files in the background. 

Instead of using Spring's default executor, I always configure a custom ThreadPoolTaskExecutor in production, 
and if the application has different types of workloads, I split them into separate named thread pools.
For example, one pool for core business logic like order processing and another for background tasks like notifications,
so they don't interfere with each other. 

A concrete example is an order confirmation flow where sending an email, sending an SMS, and updating inventory are all independent — I fire all three as CompletableFuture tasks
and use CompletableFuture.allOf().join() to run them in parallel and wait for all to finish, instead of calling them one by one. 
Finally, whenever threads share state, I use Java concurrency tools like AtomicInteger, ConcurrentHashMap, or ReentrantLock to prevent race conditions.

### What annotations do we use to configure customized Actuator?

Spring Boot Actuator provides production-ready monitoring endpoints. 
I normally configure and expose existing endpoints like health, metrics, and prometheus in application.yml, then connect Prometheus to scrape the data and Grafana to visualize it.

For custom endpoints, I use @Endpoint to define the class as a custom Actuator endpoint, and inside it I use @ReadOperation for GET-style reads, 
@WriteOperation for updates, and @DeleteOperation for deletions — these map to HTTP methods automatically when the endpoint is exposed over the web.

### How does Spring IOC work?

IoC stands for Inversion of Control. 
The whole flow is: scan class annotation, register them as bean, manage bean scopes and lifecycle, and inject dependencies.

Instead of the application creating and managing objects manually with NEW, we use Spring container, which controls the lifecycle and wiring of all objects. 
When the application starts, Spring scans for classes annotated with @RestController, @Controller, @Service, @Repository, or @Component, registers them as beans in the ApplicationContext, 
and then automatically injects dependencies wherever @Autowired is used. 

By default all beans are singleton scoped, meaning Spring creates one instance and reuses it throughout the application, 
but we can change this with @Scope to prototype, request, or session if needed. 

The main benefit is that it decouples object creation from business logic, which makes the code much easier to test.
Ex: in unit tests we can inject a mock instead of the real dependency without changing any application code.

### Could AOP apply to a private method?

No, Spring AOP cannot apply to private methods because Spring AOP is proxy-based. 
When Spring applies AOP, it wraps the target bean in a proxy, and the proxy can only intercept public method calls coming from outside the class. 

If a private method is called internally within the same class, it bypasses the proxy entirely and AOP advice never gets triggered. 
If we truly need to intercept private methods, we would have to use AspectJ with compile-time or load-time weaving instead of Spring AOP,
since AspectJ operates directly on the bytecode rather than through proxies. 

In practice though, if I find myself needing AOP on a private method, it's usually a sign to refactor — 
either make the method package-private or extract it into a separate bean so Spring's proxy can intercept it properly.
