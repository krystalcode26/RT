What is Docker, Dockerfile, Docker Image, Docker Container

Docker is a containerization platform that packages your application and all its dependencies into a lightweight, portable unit that runs consistently across any environment — dev, staging, and production.
Dockerfile is a text file containing step-by-step instructions to build a Docker image — it defines the base OS, installs dependencies, copies application code, and sets the startup command.
Docker Image is the built artifact from a Dockerfile — a read-only, layered snapshot of your application and its environment. Think of it like a blueprint or a class in Java.
Docker Container is a running instance of a Docker image — it's the actual live process. Think of it like an object instantiated from a class.

Q2. Docker vs VM
A VM (Virtual Machine) virtualizes the entire hardware stack — 
each VM has its own full OS, kernel, and system libraries, managed by a hypervisor, making them heavy (GBs) and slow to start (minutes). 
Docker containers share the host OS kernel and only package the application and its dependencies, making them lightweight (MBs) and fast to start (seconds). 
The tradeoff is isolation — VMs provide stronger security boundaries since each has its own kernel, 
while containers share the host kernel and rely on Linux namespaces and cgroups for isolation.


Q3. How to use Docker in a real project
In a real Spring Boot microservices project, each service has its own Dockerfile using a multi-stage build to keep the final image small:
dockerfile
# Stage 1: Build
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: Run
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/order-service.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
For local development, Docker Compose runs all services together:
yaml# docker-compose.yml
services:
  order-service:
    build: ./order-service
    ports:
      - "8080:8080"
    environment:
      - SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/orders
    depends_on:
      - postgres
      - kafka

  postgres:
    image: postgres:15
    environment:
      POSTGRES_DB: orders
      POSTGRES_PASSWORD: secret

  kafka:
    image: confluentinc/cp-kafka:latest
In CI/CD, GitHub Actions builds the image, pushes to ECR, and deploys to EKS:
Code push → GitHub Actions → docker build → push to ECR → helm upgrade → EKS


EC2 — Elastic Compute Cloud
A virtual machine in the cloud where you have full OS-level control — CPU, memory, storage, and network.
How I use it in project:
Use cases in project:
- Host Jenkins CI/CD server
- Run Kafka brokers
- Host Bastion host for secure SSH access to private subnets
- Run specialized GPU workloads for ML inference
Architecture:
Internet → ALB → EC2 instances (in private subnet)
                      ↓
                   RDS (private subnet)
In production I place EC2 instances in private subnets behind an ALB, assign them an IAM role for S3/Secrets Manager access, and attach them to an ASG for automatic horizontal scaling based on CPU CloudWatch alarms.

ECS — Elastic Container Service
AWS's managed container orchestration service that runs Docker containers on EC2 or Fargate without managing Kubernetes.

Use cases in project:
- Run Spring Boot microservices as ECS tasks
- Fargate mode → no EC2 node management
- Task definitions define CPU, memory, image, env vars
- Service auto-restarts failed tasks
Architecture:
ECR (image registry)
      ↓
ECS Task Definition (CPU: 512, Memory: 1024, Image: ecr/order-service:sha)
      ↓
ECS Service (desired count: 3, ALB target group)
      ↓
Fargate (serverless compute)
ECS Service connects to an ALB target group, automatically registers new tasks and deregisters unhealthy ones, pulling secrets from Secrets Manager at task startup.

ECR — Elastic Container Registry
AWS's fully managed private Docker image registry for storing, versioning, and deploying container images.

CI/CD pipeline flow:

    ↓

    ↓
docker tag order-service:latest 
  123456789.dkr.ecr.us-east-1.amazonaws.com/order-service:git-sha

Use cases in project:

DocumentDB
AWS's fully managed MongoDB-compatible document database for storing semi-structured JSON data with automatic replication across 3 AZs.

Use cases in project:
- Product catalog with flexible schema (varying attributes per category)
- User activity logs with nested JSON structure
- Content management system storing rich text documents
Architecture:
Product Service (Spring Boot + Spring Data MongoDB)
    ↓
DocumentDB Cluster (MongoDB-compatible API)

DynamoDB
AWS's fully managed NoSQL key-value and document database delivering single-digit millisecond performance at any scale.

Use cases in project:
- Session store (userId → session data, TTL: 30 min)
- Shopping cart (userId → cart items)
- Rate limiting counters (API key → request count)
- Real-time leaderboards (game scores)
Table design example — Session Store:
Partition Key: userId (String)
Sort Key: sessionId (String)
Attributes: { token, expiresAt, userAgent }
TTL: expiresAt (auto-delete expired sessions)
For high-read scenarios I enable DAX (DynamoDB Accelerator) as an in-memory cache reducing latency to microseconds. DynamoDB Streams trigger Lambda for real-time downstream event processing.

Lambda Function
Serverless compute that runs code in response to events without managing servers — charged per invocation and execution duration.

Use cases in project:
- Process S3 upload events (resize images, parse CSVs)
- Consume DynamoDB Streams (sync data to Elasticsearch)
- Scheduled jobs via EventBridge (nightly cleanup, reports)
- SNS/SQS consumer for lightweight event processing
- API Gateway backend for simple CRUD endpoints
Event-driven architecture:
S3 upload event
    ↓
Lambda triggered automatically
    ↓
Resize image → store thumbnail back to S3
    ↓
Publish SNS notification → SQS → downstream service
Cold start mitigation: Provisioned Concurrency for latency-sensitive Lambdas, SnapStart for Java runtimes, and minimal package size by excluding unused dependencies.

IAM — Identity and Access Management
AWS's service for controlling who can access what in your AWS account — managing users, roles, groups, and policies.

Key concepts:
- User    → human identity (developer, admin)
- Role    → service identity (EC2, Lambda, ECS task)
- Policy  → JSON document defining permissions
- Group   → collection of users sharing policies
Real project usage:

1. ECS Task Role
   → allows Order Service to read from S3
   → allows Order Service to publish to SNS
   → allows Order Service to read from Secrets Manager
   Policy: { "Action": ["s3:GetObject", "sns:Publish", 
             "secretsmanager:GetSecretValue"] }

2. CI/CD Role (GitHub Actions)
   → allows pushing to ECR
   → allows updating ECS services
   Policy: { "Action": ["ecr:PutImage", 
             "ecs:UpdateService"] }

3. Developer Group
   → read-only access to CloudWatch logs
   → no access to production RDS
Principle of least privilege — every role gets only the minimum permissions needed. Never use root account or hardcode access keys in application code.

SNS & SQS

SNS (Simple Notification Service) — pub/sub messaging that pushes messages to multiple subscribers simultaneously
SQS (Simple Queue Service) — message queue that durably stores messages until consumers pull and process them

Fan-out pattern in Order Service:

Order placed
    ↓
Order Service publishes to SNS topic: "order-events"
    ↓
SNS fans out to multiple SQS queues:
    ├── inventory-queue → Inventory Service decrements stock
    ├── notification-queue → Notification Service sends email
    ├── analytics-queue → Analytics Service updates dashboard
    └── audit-queue → Audit Service logs the event
Why SQS after SNS:
SNS alone → if subscriber down, message LOST
SNS + SQS → message durably stored in queue
           → consumer processes when ready
           → visibility timeout prevents duplicate processing
           → Dead Letter Queue captures failed messages after 3 retries
Code example — publish to SNS:
@Service
public class OrderService {
    
    @Autowired
    private SnsClient snsClient;
    
    public void placeOrder(Order order) {
        // save order
        orderRepository.save(order);
        
        // publish event to SNS
        snsClient.publish(PublishRequest.builder()
            .topicArn("arn:aws:sns:us-east-1:123:order-events")
            .message(objectMapper.writeValueAsString(order))
            .build());
    }
}

// SQS Consumer in Inventory Service:
@SqsListener("inventory-queue")
public void handleOrderEvent(String message) {
    Order order = objectMapper.readValue(message, Order.class);
    inventoryService.decrementStock(order.getProductId());
}
