1. Point-to-point vs Publish-subscribe

Point-to-point is like a work queue: one task should be handled by one worker. 
Publish-subscribe is like broadcasting an event: many services can receive the same message and do different things. 
I choose point-to-point for job processing, and pub-sub for event-driven architecture.

2. Why use a message system?
A message system decouples services. Instead of Service A directly calling Service B and waiting, Service A sends a message to a broker, and Service B processes it later.

We use a message system to decouple producers and consumers. 
It helps absorb traffic spikes, supports retry, and prevents one slow service from blocking the whole system. 
It is useful when we need asynchronous processing or event-driven communication.

3. Kafka architecture

Kafka is a distributed event streaming platform. Data is written to topics, and each topic is split into partitions. 
Producers write messages to topics, brokers store the data, and consumers read data using offsets. 
Kafka stores consumer progress using offsets, so consumers can resume from where they stopped.

4. Kafka messages accumulated; consumer cannot keep up. What should you do?

If Kafka messages accumulate, I first check consumer lag and identify whether the bottleneck is consumer count, partition count, or downstream processing. 
Then I scale consumers, increase partitions if needed, optimize processing, and possibly increase retention to avoid data loss. 
If the data is not critical, we may reset offsets, but for business-critical events we should process the backlog safely.

5. How does Kafka deal with expired data?

Kafka handles expired data through retention policies. Messages are stored in partition logs and deleted when they exceed configured time or size limits. Kafka deletion is independent of whether consumers have consumed the message, so retention must be configured carefully.

6. Data volume in Kafka

Kafka data volume depends on:

messages per second × average message size × retention time × replication factor
Example:10,000 messages/sec × 1 KB × 86,400 seconds/day = about 864 GB/day
With replication factor 3: 864 GB × 3 = about 2.6 TB/day
Also consider compression, indexes, logs, and replication overhead.

7. How to calculate partition number?

Use throughput and parallelism. I calculate Kafka partitions based on expected throughput, consumer parallelism, and ordering requirements. More partitions improve parallelism, but too many partitions increase overhead and rebalance cost. 
Usually I estimate traffic first, benchmark one partition, then choose enough partitions for current load plus future growth.

8. AWS SQS vs RabbitMQ vs Kafka

I use AWS SQS for simple asynchronous task processing because it's fully managed, highly available, and integrates well with AWS services.
I use RabbitMQ when I need advanced message routing, request-response patterns, or low-latency messaging between applications.
I choose Kafka for high-throughput event streaming, event replay, and real-time analytics because it stores messages for a configurable retention period and allows multiple consumer groups to read the same data independently.

9. AWS SNS vs SQS
SNS	                                                  SQS
Pub-sub notification service	                Queue service
Pushes messages to subscribers	              Consumers poll messages
One message can go to many subscribers	      One message is usually processed by one consumer
Good for fanout	                              Good for buffering and retry
Does not store messages like a queue	        Stores messages until consumed or expired

AWS SNS can fan out one message to multiple SQS queues, Lambda functions, HTTP endpoints, email, or mobile push subscribers.
SNS is for broadcasting events to multiple subscribers, while SQS is for storing messages until a consumer processes them. 
If I need fanout, I use SNS. If I need buffering, retry, and reliable task processing, I use SQS. 
A common AWS pattern is SNS + SQS, where SNS broadcasts and each subscriber has its own SQS queue.
