### 2. Clustered Index vs Non-Clustered Index
A clustered index determines the physical order of data stored in a table. Because the data itself is stored according to the clustered index, only one clustered index can exist per table. 
Default as primary key.

A non-clustered index stores index values separately from the actual table data and contains pointers to the corresponding rows. 
Multiple non-clustered indexes can be created on a table to optimize different query patterns.
 
### 3. What Data Structure Is Used for an Index?
Most relational databases use B-Tree or B+ Tree data structures to implement indexes. These balanced tree structures provide efficient search, insertion, and deletion operations with a time complexity of O(log n). 
B+ Trees are especially useful because all data records are stored at the leaf nodes, making range queries efficient. Some databases also support hash indexes for equality searches and specialized indexes for unique use cases.
 
### 4. View vs Stored Procedure
A view is a virtual table created from the result of a SQL query and does not store data itself. It is commonly used to simplify complex queries and restrict access to specific columns. 
A stored procedure is a collection of SQL statements stored and executed on the database server. Stored procedures can accept parameters, contain business logic, and perform multiple database operations in a single execution.
 
### 5. View vs Materialized View
A view stores only the SQL query definition and retrieves fresh data whenever it is accessed. A materialized view stores the actual query results physically in the database. Because the data is precomputed, materialized views provide faster query performance for complex reports and analytics. 
However, materialized views require periodic refreshes to keep the stored data synchronized with the underlying tables.
 
### 6. How to Tune SQL Queries
SQL query tuning is the process of improving query performance and reducing execution time. 
Common techniques include creating appropriate indexes, avoiding unnecessary columns in SELECT statements, and optimizing JOIN operations. 
Developers can use tools such as EXPLAIN to analyze execution plans and identify bottlenecks. 
Effective query tuning reduces database load, improves response times, and enhances overall application performance.

### 7. Saga v.s. 2PC

2PC is a synchronous, blocking protocol that ensures atomicity across distributed nodes.
It moves complexity into the infrastructure. 

Saga is a sequence of local transactions, each publishing events or messages that trigger the next step. 
Failed steps trigger compensating transactions to undo prior work.
It moves complexity into the application — you must think carefully about compensation logic and accept that the world may briefly see inconsistent state.

Most modern microservice architectures prefer Saga for its resilience, but 2PC still dominates within traditional RDBMS clusters where strong consistency is non-negotiable.

### 8. Find the average salary per department, only for employees older than30, ordered by average salary descending order.  -> EXPLINA execution plan 

SELECT d.deptname,
       AVG(e.salary) AS avg_salary
FROM employee e
JOIN department d ON e.empid = d.deptid
WHERE e.age < 30
GROUP BY d.deptname
HAVING AVG(e.salary) IS NOT NULL
ORDER BY avg_salary DESC;
