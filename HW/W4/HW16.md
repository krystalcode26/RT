1. Design Pattern Use Cases — Banking, E-Commerce, Health Insurance
Singleton: ensures only one instance of a class exists throughout the application lifecycle.
In banking, the Singleton pattern is applied to an ExchangeRateService so that all currency conversions across the application share the same cached rates without making redundant external API calls. 
In e-commerce, a single InventoryCacheManager instance serves all product availability checks, ensuring consistent inventory state throughout the request lifecycle. 
In health insurance, a shared EligibilityRuleConfig holds benefit rules loaded once at startup and reused across all eligibility evaluations without repeated database reads.
Factory: centralizes object creation logic behind a common interface, allowing the caller to request a type without knowing the concrete class.
In banking, a factory creates the correct account type: SavingAccount, CheckingAccount, or LoanAccount. 
It based on the account type code provided, so the caller never needs to know the concrete class. 
In e-commerce, a payment processor factory returns the appropriate implementation: CreditCardProcessor, PayPalProcessor, or ApplePayProcessor. 
It based on the user's selected payment method at checkout. 
In health insurance, a claim processor factory instantiates the correct handler : DentalClaimProcessor, MedicalClaimProcessor, or VisionClaimProcessor.
It based on the claim type submitted by the provider.
Builder: separates the construction of a complex object from its representation, allowing it to be assembled step by step.
In banking, a LoanApplicationBuilder assembles a LoanApplication step by step. Ex: setting applicant details, loan amount, term, collateral, and credit score before producing the final immutable object. 
In e-commerce, an OrderBuilder constructs an Order by chaining line items, coupon codes, tax calculations, shipping options, and payment details, making the construction readable and flexible. 
In health insurance, a PolicyBuilder assembles an InsurancePolicy by attaching member information, selected plan, deductible amount, and copay structure incrementally before producing the final policy object.
Proxy: controls access to another object by acting as an intermediary, typically adding security, logging, or lazy initialization without changing the real object.
In banking, a security proxy intercepts calls to the account balance service and verifies the caller's role and permissions before delegating to the real service, keeping authorization logic out of the core domain. 
In e-commerce, a proxy sits in front of the product image service or payment service to enforce access control or cache expensive responses, reducing load on the underlying service. 
In health insurance, a proxy validates that the requesting user holds the appropriate role before allowing access to patient claim details, ensuring sensitive data is never exposed without proper authorization.

2. What is Microservice Architecture?
Microservice architecture means building one application as many small, independent services.
Each service owns one business capability, such as user service, payment service, order service, or notification service.
Each service can have its own database, deploy independently, and communicate through REST API, message queue, or gRPC.

3. Why Microservice Architecture?
Microservices are useful when the system becomes large and one monolithic application is hard to maintain.
They allow teams to develop, test, scale, and deploy services independently.

Ex: in e-commerce, the payment service can scale separately during checkout traffic without scaling the whole application.

4. Main Components of Microservice Architecture
- API Gateway
Entry point for clients. It routes requests to different services. 
- Service Discovery
Helps services find each other dynamically, such as Eureka, Consul, or Zookeeper. 
Zookeeper(distributed coordination, naming, configuration, and synchronization.)
- Config Server
Central place to manage application configuration for different environments. 
- Load Balancer
Distributes requests across multiple service instances. 
- Circuit Breaker
Prevents cascading failure protects the system when one service is down. 
Ex: Resilience4j uses states like CLOSED, OPEN, and HALF_OPEN. 
- Distributed Tracing
Tracks one request across multiple services, such as Zipkin/Sleuth. 
- Centralized Logging
Collects logs from all services, commonly using ELK. (Elasticsearch, Logstash, Kibana)
- Database per Service
Each service owns its own data to reduce tight coupling. 
5. Terms to Know
Config Server
Spring Cloud Config provides centralized external configuration for distributed systems. 
It lets multiple services read configuration from one central source instead of hardcoding values in each service. 
@SpringBootApplication
@EnableConfigServer
public class ConfigServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(ConfigServerApplication.class, args);
    }
}

Service Discovery: Eureka, Consul, Zookeeper
Service discovery allows services to register themselves and find other services dynamically. 
Spring Cloud Netflix supports Eureka for service discovery. 
Consul can discover, track, and monitor service health in a network. 
Zookeeper is often used for distributed coordination, naming, configuration, and synchronization. 
Example Eureka client:
@SpringBootApplication
@EnableDiscoveryClient
public class OrderServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }
}

Zipkin and Sleuth
Sleuth adds trace IDs and span IDs to requests so logs from multiple services can be connected. 
Zipkin visualizes distributed tracing and helps find which service is slow. Spring Cloud Sleuth integrates with OpenZipkin-compatible systems. 

Ribbon
Ribbon is a client-side load balancer. It chooses which service instance to call from the client side. 
In modern Spring Cloud, Ribbon is mostly replaced by Spring Cloud LoadBalancer. Spring’s guide now uses Spring Cloud LoadBalancer for client-side load balancing. 

ELK: Elasticsearch, Logstash, Kibana
ELK is used for centralized logging. 
Elasticsearch stores and searches logs.
Logstash collects and processes logs
Kibana visualizes logs with dashboards. 
Elastic describes the stack as tools for ingesting, storing, searching, analyzing, and visualizing data. 

Circuit Breaker: Hystrix → Resilience4j
Circuit breaker protects the system when a downstream service fails. 
If failures pass a threshold, the circuit opens and calls go to fallback instead of repeatedly calling the broken service. 
Resilience4j uses states like CLOSED, OPEN, and HALF_OPEN. 
@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
public String callPaymentService() {
    return restTemplate.getForObject("http://payment-service/pay", String.class);
}

public String paymentFallback(Exception ex) {
    return "Payment service is temporarily unavailable.";
}
