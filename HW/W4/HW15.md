### JDBC vs Hibernate
Both of them are used by Java applications to access relational databases.

JDBC is a low-level Java API that requires you to write raw SQL and manage connections manually. It also requires you to convert ResultSets into Java objects manually, which leads to repetitive boilerplate code across every repository.
Ex: use when need full control over complex SQL queries or performance-critical operations

Hibernate is a high-level ORM framework that maps Java classes to database tables automatically. It generates SQL based on entity mapping and handles connection pooling, caching, and transactions, dramatically reducing boilerplate.

Ex: use for CRUD-heavy applications where we want to reduce boilerplate and keep the code database-agnostic.

### Statement vs PreparedStatement vs CallableStatement 
All of them are JDBC interfaces used to execute SQL statements against a database.

Statement executes raw SQL strings directly. Because it uses string concatenation to build queries, it is vulnerable to SQL injection and recompiles the SQL every time it is executed. 
Ex: Best used for static SQL like DDL statements such as CREATE or DROP.

PreparedStatement uses ? placeholders to separate SQL structure from user input, making it safe from SQL injection. It is pre-compiled once and reused for repeated executions, which improves performance. Ex: Best used for parameterized queries and DML operations like INSERT, UPDATE, and DELETE.

CallableStatement extends PreparedStatement to support calling stored procedures in the database. 
It supports IN parameters for input, OUT parameters for output, and INOUT parameters for both. 
Ex: Best when business logic is encapsulated inside a stored procedure.

-> PreparedStatement is the default choice for any query involving user input. Statement should be avoided for dynamic queries, and CallableStatement is used when the team decides to manage logic at the database level.

### SQL Injection 
It is prevented by never concatenating user input into SQL strings.
Instead use PreparedStatement, named parameters in HQL/JPQL, input validation, or stored procedures.

### ORM 
ORM is Object-Relational Mapping is the technique of bridging Java objects and relational tables, so you work with classes and fields instead of tables and columns. the framework generates the SQL automatically based on your class structure.

### JPA vs Hibernate 
JPA is a specification (just interfaces and annotations like @Entity, @Id) with no implementation so it cannot perform database operations by itself must relied on other provider such as Hibernates.

Hibernate is a high-level ORM framework also implementation of that spec, adding extras like Session, HQL, and L1/L2 caching.
Ex: code to the JPA interface and let Hibernate be the provider underneath.

### Entity Lifecycle has four states: 
Transient (created with new, no DB row)
Persistent (attached to a Session, changes auto-synced via dirty checking)
Detached (session closed, changes not tracked)
Removed (scheduled for deletion on the next commit).

### Mapping relationships 
Mapping relationships used to represent associations between entity classes and map those relationships to database table.

Ex: @OneToOne, @OneToMany/@ManyToOne, and @ManyToMany.

The owning side holds the @JoinTable or @JoinColumn, while the inverse side uses mappedBy to avoid creating a duplicate join table.

### Cascade types 
Cascade types control which operations propagate from parent to child.
There are six types:

PERSIST: parent entity is saved, child entities are also saved automatically.
MERGE: the parent entity is merged, the child entities are also merged.
REMOVE: parent entity is deleted, the child entities are also deleted!!!
REFRESH: the parent entity is refreshed, the child entities are also reloads from the database.
DETACH: the parent entity is detached, the child entities are also detached from the session.
ALL: includes all of the above cascade types.

Use case: CascadeType.PERSIST and CascadeType.MERGE for most parent-child relationships where the child cannot exist without the parent, such as an order and its order items. 

!!! REMOVE on a shared entity can cause unintended deletions.
Avoid CascadeType.REMOVE on @ManyToMany relationships because the child entity is shared between multiple parents. Deleting one parent would unintentionally delete the shared child and break other relationships, so in that case we handle deletion manually instead.

### Fetch types 
It control when related data loads: 
EAGER loads it immediately in the same query (By default for @ManyToOne)

LAZY loads it on-demand via a proxy (By default for collections, @OneToMany and @ManyToMany )
LAZY can cause N+1 queries, which is solved by using JOIN FETCH in HQL.

### First and second level cache
Both are used to reduce repeated database queries and improve ORM query performance.

First-level cache is per-Session(belongs to a single EntityManager or Hibernate Session), so it cannot be shared across different sessions. 
It always enabled, and prevents duplicate queries within one transaction.
I

Second-level cache belongs to the entire EntityManagerFactory or SessionFactory so it shared across all Sessions. It must be configured with a provider like Ehcache, and is ideal for frequently-read, rarely-changed data.


### Joins
INNER JOIN returns only matching rows from both tables
LEFT JOIN returns all left rows plus matches from the right
RIGHT JOIN returns all right rows plus matches from the left
FULL OUTER JOIN returns everything from both sides with NULLs where unmatched
CROSS JOIN produces a Cartesian product of every row combination.

### UNION vs UNION ALL
Both stack result sets vertically and require matching column counts and compatible types, but UNION removes duplicates (slower, requires a sort).

UNION ALL keeps every row including duplicates (faster) — prefer UNION ALL unless deduplication is genuinely required.
